## 🛠️ Die 3 goldenen Leitplanken für Ihren "Archäologie-Sprint"

Wenn Sie diesen Weg wählen (erst kartieren, dann bauen), müssen die Kriterien absolut unerbittlich sein:

### 1. Der "Genesis-Blindtest" (Die wichtigste Regel!)

ChatGPT hat es perfekt formuliert: *Versteht man das Modul, ohne die Genesis-Story zu kennen?*
Ich würde das technisch radikaler ausdrücken:

> **Würde ein externer Entwickler dieses Modul in einem völlig anderen Kontext (z. B. für Logistik-Optimierung oder IoT-Datenströme) installieren wollen?**

Wenn Sie ein Paket wie `entropy-table` oder `utac-core` isoliert betrachten: Macht es als mathematisch-technisches Werkzeug Sinn? Wenn ja $\rightarrow$ Core-Kandidat. Wenn es nur existiert, um "kosmische Resonanzen" abzubilden $\rightarrow$ Bleibt im Labor.

### 2. Inventarisierung via Code, nicht via Prosa

Nutzen Sie für die Inventarisierung kein leeres Wiki, sondern Ihr bereits existierendes Werkzeug: **Scope**.

* Verwenden Sie Code-Analysetools (AST-Parser), um die echten Abhängigkeiten der 48 Repositories automatisiert zu plotten.
* Messen Sie die *tatsächliche* Kopplung. Oft glaubt man, ein Modul sei "Core", aber in der Realität wird es nur von zwei Legacy-Paketen importiert.

### 3. Das "Graveyard"-Konzept operationalisieren

Ein Friedhof für Code ist gut, aber ein **"Deprecation & Plugin-Protokoll"** ist besser. Der Core darf *niemals* direkt von einem Plugin wissen. Der Core stellt Schnittstellen bereit (z. B. via `Protocol` in Python oder abstrakte Basisklassen). Ob ein Plugin dann `utac-mandala` oder `industry-scheduler` heißt, muss dem Core-Monorepo architektonisch völlig egal sein.
